# 면접 질문 생성: 무료 모델을 두고 유료 모델을 고른 이유

> 면접 정하기에서 고른 직무로 질문 8개를 만드는 기능에 쓸 모델을 골랐다. 처음 계획은 무료 플랜이 있는 Groq의 오픈 모델이었다. 같은 직무 12개를 돌려 출처를 가린 평가자 3명에게 맡기자, 유료 모델(OpenAI Luna)이 **세 평가자 모두에서 12개 직무 전부 1위**였다. 규칙 위반은 직무당 **0.7개 대 4.0~5.1개**였다. 한 번에 약 0.2원이고 약 4초 걸리며, 화면에서는 버튼에 마우스를 올릴 때 미리 만들어 기다림을 줄였다.
>
> 상태: 서비스에 반영(2026-10). 직무·경력별 서버 캐시와 IP당 하루 요청 제한을 붙였다(머지 전, 2026-10).

## 문제 상황

intervgym의 첫 단계(면접 정하기)는 직무와 경력(신입·경력, 경력이면 연차)을 받는다. 그런데 이 값이 실제로 쓰이는 곳이 거의 없었다.

| 입력 | 쓰이던 곳 |
| --- | --- |
| 직무 | 화면 제목에만. 직무 맞춤 탭은 어떤 직무를 골라도 시안의 프론트엔드 예시 질문 7개였다 |
| 경력 | 질문 풀을 신입용·경력용으로 나누는 데만 |
| 연차 | 어디에도 |

간호사를 골라도 "React 상태 관리" 질문이 나왔다. 배포해서 사용자 피드백을 받기 전에 첫 단계가 제 역할을 하게 만들어야 했다. 직무 목록은 한국고용직업분류를 바탕으로 한 581개라, 미리 질문을 써 둘 수는 없고 생성해야 했다.

## 처음 계획: 무료 모델

계획은 Groq였다. 이미 답변 받아쓰기(Whisper)에 쓰고 있었고, 무료 플랜이 있으며 빠르다. 질문 만들기는 답변을 읽고 판단하는 피드백보다 쉬운 일이라 작은 모델로 충분하다고 봤다.

직무 8개(신입·경력 섞어서)를 같은 프롬프트로 세 모델에 돌렸다.

| | `gpt-oss-20b` (Groq) | `gpt-oss-120b` (Groq) | Luna (OpenAI) |
| --- | --- | --- | --- |
| 걸린 시간 | 0.5~1.3초 | 0.8~1.1초 | 4.8~6.8초 |
| 질문 8개를 지켰나 | 2개 직무에서 7개만 냄 | 모두 지킴 | 모두 지킴 |
| 경력 반영 | 간호사 3년차에게 "과거 실습에서 가장 기억에 남는 케이스는 무엇이며, 그 이유는?" | 3년차에 맞는 질문 | 3년차에 맞는 질문 |
| 문장 | "차이점은?" 같은 반쪽 문장, 오타("에스프레션") | 대체로 완전한 문장 | 완전한 문장 |

20b는 여기서 뺐다. 120b는 쓸 만해 보였고, 가격(100만 토큰당 $0.15/$0.60, 한 번에 약 0.3원)도 Luna($0.10/$0.50, 약 0.2원)와 비슷했다. 그래서 갈리는 건 품질, 속도, 무료 한도였다.

## 평가 방법

- **직무 12개:** 신입 6, 경력 6. 처음 시험에 없던 직무 7개를 넣었다(물류, 기술 영업, 인테리어 디자이너, 간호조무사, 특수교사, 제품 디자이너, 영업 지원).
- **세 가지:** 120b 생각 낮게, 120b 생각 중간, Luna 생각 끔. 120b는 프롬프트를 고쳐서(v2) 한 번 더 기회를 줬다.
- **평가자 3명(AI):** 출처를 가리고 직무마다 섞은 라벨로 순위를 매겼다. 관점을 나눴다.
  - 그 직무의 면접관: 실제로 나올 법한가
  - 연습하는 지원자: 신입이 답할 수 있나, 경력에 맞는 깊이인가
  - 규칙 검수: 질문마다 위반을 셈
- **규칙:** 한 질문에 하나만 묻기, 신입에게 특정 배경(대학·인턴) 짐작 금지, 경력자에게 학교·자격증 질문 금지, 질문에 연차 숫자 금지, 공통 질문 섞지 않기 등.

## 결과

| | 120b 생각 낮게 | 120b 생각 중간 | Luna 생각 끔 |
| --- | --- | --- | --- |
| 1위 (면접관 / 지원자 / 검수, 각 12개 중) | 0 / 0 / 0 | 0 / 0 / 0 | **12 / 12 / 12** |
| 규칙 위반 (12개 직무 합) | 61개 (직무당 5.1) | 48개 (직무당 4.0) | **8개 (직무당 0.7)** |
| 위반이 없는 직무 | 0 | 0 | 6 |
| 걸린 시간 (가운데값) | 1.0초 | 3.0초 | 4.2초 |
| 무료 한도 | 버팀 | 12번 부르는 동안 14번 대기 | 해당 없음 |

120b는 프롬프트에 금지라고 적은 실수를 그대로 되풀이했다. 간호사 3년차에게 "대학 실습 때 급성 호흡곤란 환자를 돌본 경험", 제품 디자이너 8년차에게 "대학 시절 팀 프로젝트"를 물었다. "5년 차 회계 담당자로서"처럼 연차를 질문에 넣었고, 하지 않았을 수도 있는 "회계 시스템 도입 프로젝트"를 전제했다. 면접관 관점 평가자가 "그대로 내보낼 수 없다"고 꼽은 5개 묶음은 모두 120b 생각 낮게였다.

같은 직무를 비교하면 차이가 잘 보인다.

| | 판금원 신입 |
| --- | --- |
| 120b | 용접과 판금 가공을 병행할 때 주의해야 할 점은 무엇인가요? |
| Luna | 판재를 굽힐 때 원하는 각도와 치수를 맞추려면 어떻게 작업하나요? |

## 무료가 무료가 아니었던 이유

120b를 고를 이유는 속도(약 1초)와 무료였다. 그런데 품질을 맞추려고 생각을 중간으로 올리자 두 가지가 같이 사라졌다.

- **속도:** 생각을 올리면 약 3초가 되어 Luna(약 4초)와 차이가 거의 없어졌다.
- **무료 한도:** Groq 무료 플랜의 `gpt-oss-120b` 한도는 하루 1,000번, 분당 8,000토큰이다. 한 번에 약 900토큰을 쓰니 분당 9번 남짓이다. 생각을 올린 시험에서는 12번 부르는 동안 14번을 기다렸다. 이 한도는 앱의 모든 사용자가 같이 쓴다. 피드백을 받으려고 링크를 뿌리는 날 막힐 수 있다.

반대로 Luna는 생각을 꺼도(`reasoning_effort: none`) 품질 차이가 눈에 띄지 않았고, 시간은 4.8~6.8초에서 **2.8~4.4초**로 줄었다. 한 번에 약 0.2원이라 비용으로 고를 일이 아니었다. 피드백에 이미 쓰는 모델이라 호출 코드와 키도 늘지 않았다.

## 프롬프트로 안 되는 건 코드로

모델을 정한 뒤 프롬프트를 두 번 더 고쳤다(v3, v4). 평가자는 새 직무 12개로 다시 붙였다.

- **v2 → v3:** 신입 경험 질문이 직무마다 "학교나 실습에서 / 자격증을 준비하며 / 아르바이트나 팀 활동에서"로 시작했다. 내가 프롬프트에 넣은 예시 문구를 그대로 따라 쓴 것이었다. 예시를 빼고 "경험을 어디서 했는지는 지원자가 고르게 둔다"로 바꾸자, 규칙 위반이 **32개 → 9개**로 줄었다. 면접관 평가자 기준으로 v3가 10개 직무에서 이기고 2개는 비슷했다.
- **v3 → v4:** "확인하고 처리하나요"처럼 두 동작 묻기, "우선순위를 정한 경험"처럼 어느 직무에나 붙는 질문을 금지했다. 지원자 관점 7:1, 면접관 관점 6:3으로 v4가 앞섰다.

v4에서 요즘 면접에 나오는 **AI 도구 활용 질문**을 최대 1개 넣기로 했다. 문서·코드·데이터를 만드는 직무에는 자연스럽지만, 정비사나 유치원교사에게는 어색하다. 그래서 프롬프트에 "그 직무에서 AI 도구를 쓰는 게 자연스러울 때만, 애매하면 넣지 않는다"고 썼다.

모델은 12개 직무 **전부**에 넣었다. 문장을 더 강하게 바꿔도(현장 작업·돌봄·의료 직무는 넣지 말라고 나열) 결과가 같았다. 유치원교사에게 "AI 도구가 제안한 유아 활동 계획을 검토할 때, 어떤 기준으로 적절성을 판단하나요?"가 나왔다.

넣을지 말지를 모델에게 맡기지 않기로 했다. 코드가 직무 분야(직무 목록의 34개 분야 중 10개)로 정하고, 그중에서도 절반 확률로만 "AI 활용 질문: 넣기"를 입력에 적는다. 모델은 "넣기"라고 적혀 있으면 정확히 하나를 넣는다. 다시 돌리자 정해 둔 분야의 7개 직무에만 들어갔다.

## 결정과 이유

| 결정 | 이유 |
| --- | --- |
| 모델은 Luna, 생각 끔 | 세 평가자 모두 12개 직무 전부 1위. 생각을 꺼도 품질이 같고 2.8~4.4초 |
| Groq는 받아쓰기에만 | 품질을 맞추면 속도 장점이 사라지고 무료 한도에 걸림. Groq 한도는 모델마다 따로라 받아쓰기와 겹치지 않음 |
| AI 활용 질문 여부는 코드가 | 프롬프트로 조건을 걸어도 모든 직무에 넣음 |
| 질문은 저장하지 않음 | 연습 서비스라 다시 누르면 새 질문을 받는 게 자연스러움(사용자 판단) |
| "루틴 짜러 가기"에 마우스를 올리거나 포커스할 때 미리 만들기 | 값이 바뀔 때마다 만들면 경력을 여러 번 바꿀 때 요청이 쌓이고 늦은 응답이 앞 응답을 덮음 |

## 결과

실제 화면에서 간호사 3년차로 "루틴 짜러 가기"에 마우스를 올리고 누르자, 질문 고르기 화면에 질문 8개가 뜨기까지 **4.3초**, 요청은 **1번**이었다. 만드는 동안 공통 탭은 그대로 쓸 수 있고, "다시 만들기"를 누르면 새 질문 8개를 받는다.

나온 질문 예시(간호사 3년차):

- 투약 직전 환자 확인 과정에서 처방 정보와 환자 진술이 다르면 무엇부터 확인하나요?
- 인수인계 중 중요한 간호 정보가 빠진 것을 발견하면 누구에게 어떻게 알리나요?

## 한계와 다음 단계

- **평가자도 AI다.** 평가자는 Claude였고, 1위 묶음의 문체가 같아 출처를 완전히 가리지 못했다는 평가자 메모가 있었다. 다만 개수를 센 규칙 위반도 같은 방향이었다.
- **직무마다 한 번씩만 돌렸다.** 같은 직무를 여러 번 돌렸을 때의 흔들림은 재지 않았다.
- **남은 약점:** v4에도 두 동작 묻기와 경력자 경험 질문의 비슷한 틀이 조금 남아 있다. 실제 사용자 반응을 보고 고친다.
- **기다림:** 마우스를 올린 뒤 누르기까지는 1초가 안 걸리는 경우가 많아, 미리 만들기로는 다 가리지 못했다. 위 브라우저 시험(마우스를 올리고 0.8초 뒤 누름)에서는 누른 뒤 약 3.5초 "만드는 중"을 봤다. 그래서 Upstash Redis에 직무·경력 구간별 서버 캐시를 붙였다. 같은 직무를 고른 다른 사람이 같은 질문을 받아도 서로 알 수 없어서, 처음 한 사람만 기다리면 된다. 실제 DB(도쿄)에 붙여 재니 캐시에 없을 때 **6.9초**, 두 번째부터 **0.26초**였다. 연차는 구간(1~2·3~5·6년차 이상)으로 묶어 4년차가 만든 질문을 3년차도 바로 받는다. "다시 만들기"만 캐시를 건너뛰고 새로 만든다.

## 배운 점

- 무료 플랜의 값은 그 플랜으로 원하는 품질을 낼 수 있을 때만 의미가 있다. 품질을 맞추는 순간 속도와 한도 비용이 같이 올라왔다.
- 프롬프트의 예시 문구는 규칙보다 강하다. 예시를 빼는 것만으로 같은 틀 반복이 사라졌다.
- 모델이 조건을 지키지 못하는 판단은 코드로 옮긴다. 말로 부탁하는 대신, 그렇게밖에 할 수 없게 만든다.
