# 아무도 정하지 않은 import 순서를 에이전트들이 지키고 있었다

> intervgym은 Claude Code 세션 여러 개가 이어 받으며 474개 파일을 만들었다. import 순서 규칙은 문서에도 lint에도 없었다. 그런데 import가 두 종류 이상인 파일 **251개 중 225개(90%)** 가 내가 평소 정리하던 순서(라이브러리 → 위 층 → 아래 층 → 슬라이스 내부)를 지키고 있었다. FSD 층끼리의 순서만 보면 층을 둘 이상 가져오는 파일 **65개 중 56개(86%)** 였고, 깨진 9개 중 8개는 새 슬라이스를 처음 만든 PR 두 개에서 나왔다. 규칙이 지켜지고 있어서, 규칙이 없다는 걸 몰랐다. 발견한 뒤 판단이 필요 없는 부분만 lint로 굳혔다.
>
> 상태: 서비스에 반영(2026-10). import 순서와 `index.ts` 순서를 lint로 고정했다.

## 문제 상황

`shared/lib/index.ts`의 export가 뒤섞여 있어 정리하자고 하던 중이었다. 옆에 열어 둔 화면 파일의 import 블록을 보다가 이상한 점을 알아챘다.

```ts
import { useState, type ReactNode } from 'react';

import { … } from '@/features/interview/select-device';

import { … } from '@/entities/interview';
import { … } from '@/widgets/interview/recorder';

import { BottomBar, Button, ErrorBoundary } from '@/shared/ui';

import { INTERVIEW_TEXTS } from '../config/texts';

import StepFrame from './step-frame';
```

라이브러리, 레이어, 슬라이스 내부 순서로 빈 줄을 두고 나뉘어 있었다. 내가 예전 프로젝트에서 손으로 정리하던 방식 그대로였다. 이 파일만 `widgets`가 `entities` 아래로 내려가 있었다. 그런데 이 규칙을 적어 둔 곳을 찾아보니 어디에도 없었다. ARCHITECTURE 문서에도, CLAUDE.md에도, ESLint 설정에도 없었다.

## 원인: 왜 지켜졌나

재 보니 큰 줄기는 거의 지켜지고 있었다. 두 가지 기준으로 쟀다. 하나는 import 전체 순서(라이브러리 → 층 → `../` → `./`)이고, 다른 하나는 FSD 층끼리의 순서다. 둘 다 같은 층 안 알파벳 순서와 빈 줄은 보지 않았다.

| 파일을 처음 만든 시기 | import 종류 둘 이상 | 전체 순서를 지킴 | FSD 층 둘 이상 | 층 순서를 지킴 |
| --- | --- | --- | --- | --- |
| 원래 프로젝트에서 옮기기 | 79 | 68 (86%) | 20 | 20 (100%) |
| 부품 만들기 | 18 | 18 (100%) | 0 | - |
| 화면 만들기 | 125 | 115 (92%) | 43 | 34 (79%) |
| 새 기능 | 29 | 24 (82%) | 2 | 2 |
| 합계 | 251 | **225 (90%)** | 65 | **56 (86%)** |

옮겨 온 파일이 전체 순서에서 86%인 것은 대부분 `./`를 `../`보다 먼저 쓴 경우(5곳)다. 층 순서는 하나도 깨지지 않았다. 옮길 때 코드를 거의 그대로 가져왔으니, 원래 코드에서도 `./`와 `../`의 순서는 정해져 있지 않았던 것으로 보인다.

이유는 에이전트가 일하는 방식에 있다고 본다.

- **출발점이 사람 손으로 정리한 코드였다.** 첫 단계에서 원래 프로젝트의 코드를 동작을 바꾸지 않고 거의 그대로 옮겼다. 처음 쌓인 파일들이 이미 내 정리 방식을 담고 있었다.
- **에이전트는 쓰기 전에 옆 파일을 읽고 따라 쓴다.** 새 화면을 만들 때는 같은 슬라이스나 비슷한 화면의 파일을 먼저 연다. 열어 본 파일이 모두 같은 순서면 그 순서로 쓴다. Claude Code도 "주변 코드처럼 쓰라"는 지시를 기본으로 받는다.
- **따라 쓴 파일이 다음 에이전트의 예시가 된다.** 세션이 바뀌어도 예시가 계속 이어져서, 문서 없이도 순서가 유지됐다.

깨진 곳에도 패턴이 있었다. 층 순서를 어긴 9개 중 8개는 **새 위젯 슬라이스를 처음 만든 PR 두 개**(결과 화면 6개, 결산 화면 2개)에서 나왔다. 같은 슬라이스 안에 따라 할 옆 파일이 없던 경우다.

예시에서 잘 드러나지 않는 세부는 처음부터 제각각이었다. 규칙을 lint로 켜 보니 걸린 곳은 201곳(128개 파일)이었고, 대부분이 세부 차이였다.

| 걸린 이유 | 곳 |
| --- | --- |
| 같은 층 안의 순서(알파벳) | 92 |
| 묶음 사이 빈 줄이 없거나, 묶음 안에 빈 줄 | 51 |
| 테스트 도구(`@test`)와 외부 패키지 순서 | 19 |
| 같은 경로의 `type` import 위치 | 15 |
| `../`와 `./` 순서 | 8 |
| **FSD 층 순서** | **10** |

정하지 않은 부분은 에이전트마다 그때그때 달랐다. 정해진 적은 없어도 예시에서 반복된 부분은 끝까지 이어졌다.

## 시도와 버린 것

발견한 뒤 무엇을 규칙으로 만들지 정했다. 처음엔 `index.ts`의 export를 "함께 쓰는 것끼리" 묶자는 이야기에서 시작했다.

| 시도 | 결과 | 판단 |
| --- | --- | --- |
| 문서에 "주제별로 묶고 주석을 단다"를 적어 에이전트끼리 지키기 | "음성 인식과 질문 읽기는 같은 주제"처럼 뜻을 읽어야 해서 기계로 검사할 수 없다. 에이전트마다 묶는 방식이 달라지고, 매번 판단하는 데 토큰이 든다 | 버림 |
| `eslint-plugin-perfectionist`의 export 정렬 | 경로 순서 정렬은 된다. 그러나 "폴더마다 한 묶음"은 묶음마다 폴더 이름을 설정에 적어야 하고, 패키지도 하나 는다 | 버림 |
| 프로젝트 전용 lint 규칙(`index.ts`) | 문이 둘 이상인 폴더는 폴더마다 한 묶음, 하나뿐인 폴더는 끝에 모아 알파벳순. 경로만 보고 정해 `--fix`로 맞는다. 약 40줄, 패키지 추가 없음 | 채택 |
| 이미 깔린 `eslint-plugin-import`의 `import/order` | 층 순서(`@/app` → … → `@/shared`), 묶음 사이 빈 줄, 묶음 안 알파벳 순서를 전부 `--fix`로 맞출 수 있다 | 채택 |

## 결정과 이유

- **판단이 필요 없는 규칙만 둔다.** 경로만 보고 정할 수 있는 순서는 lint가 맡는다. "어떤 것끼리 관련 있나"처럼 뜻을 읽어야 하는 규칙은 두지 않는다. 검사할 수 없는 약속은 결국 다시 흔들린다.
- **암묵적으로 지켜지던 것을 그대로 굳힌다.** 새로 정한 순서가 아니라 86%가 이미 따르던 순서다. 그래서 바뀌는 건 세부와 깨진 10곳뿐이다.
- **세부까지 정한다.** 같은 층 안의 알파벳 순서처럼 지금까지 제각각이던 부분도 lint로 고정한다. 하나라도 남겨 두면 그 부분은 다시 "알아서"가 된다.

## 한계

- 원래 프로젝트의 코드와 직접 비교하지는 못했다. 옮겨 온 파일이 층 순서를 하나도 어기지 않은 것으로 간접 확인했다.
- 층 순서가 깨진 것이 파일을 처음 만들 때인지, 나중에 고칠 때인지는 가르지 못했다.
- 관찰이지 실험이 아니다. 예시 없이 같은 일을 시킨 비교군이 없어서 "옆 파일을 따라 했다"는 설명은 추정이다. 층 순서 표본은 65개 파일로 작다.
- 한 사람이 같은 모델 계열로 만든 프로젝트다. 다른 모델이나 여러 사람이 섞인 저장소에서도 같은지는 모른다.
