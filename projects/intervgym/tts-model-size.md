# 질문 읽기 TTS: 380MB 모델을 65MB로

> 생성 질문을 읽어 줄 음성을 서버 API 대신 사용자 브라우저에서 만들기로 했다. 공개 TTS 모델을 한국어·영어 버전으로 골라 처음엔 **263MB → 93MB**(int8 계산)로 줄였다. 그런데 브라우저에서 다시 재 보니 이 판이 문장당 **5~12초**로 원본보다 5배 느렸다. 숫자를 **담을 때만** int8로 하고 열 때 원래 숫자로 푸는 방식으로 바꿔 **65MB에 문장당 1.4~3.5초**(스레드 4개면 **0.7~1.0초**)가 됐다.
>
> 상태: 서비스에 반영(2026-10). 브라우저 측정으로 93MB 판을 65MB 판으로 바꿨다(2026-10). 모델을 Cloudflare R2에 올려 전용 도메인으로 열고, 앱에서 받아 읽는 것까지 확인했다(2026-10). 실제 폰·PC 측정은 배포 뒤에 한다. 고정 질문은 녹음 → 미리 만든 음성 파일로 바꿨다가, 브라우저 합성만으로 충분해 파일도 두지 않기로 했다(2026-10). 영어 용어를 한글로 적은 읽기용 문장도 두지 않기로 했다(2026-10).

## 문제 상황

intervgym은 녹화를 시작하기 전에 면접 질문을 음성으로 읽어 준다. 면접 분위기를 만드는 핵심 기능인데, 지금 방식에는 세 가지 한계가 있었다.

- **브라우저 기본 음성(`speechSynthesis`)**: 무료지만 윈도우·맥·안드로이드마다 목소리가 다르고, 한국어 음성이 없는 기기에서는 읽지 못한다.
- **클라우드 TTS**: 음질은 좋지만 글자 수만큼 과금된다. 생성 질문과 꼬리 질문까지 읽으면 사용자가 늘수록 운영비에서 큰 항목이 된다.
- **공개 모델 Supertonic 3**: 한국어를 지원하고 무료지만 모델 파일이 **380MB**다. 브라우저에서 받기엔 무겁고, Vercel 서버 함수 크기 한도에도 들어가지 않는다.

고정 질문은 처음에 직접 녹음하려 했고, 다음엔 같은 모델로 음성 파일을 미리 만들어 두려 했다. 결국 모든 질문을 브라우저에서 합성한다(아래 결정).

## 원인 분석: 무엇이 큰가

처음에는 31개 언어를 지원해서 크다고 생각했다. 한국어·영어만 남기면 확 줄 거라는 가설이었다. 하지만 같은 회사의 버전별 크기를 비교하자 가설이 바로 틀렸다.

| 버전 | 지원 언어 | 크기 |
| --- | --- | --- |
| Supertonic 1 | 영어 | 263MB |
| Supertonic 2 | 영어·한국어 등 5개 | 263MB |
| Supertonic 3 | 31개 | 398MB |

언어를 1개에서 5개로 늘려도 크기가 같았다. 언어별 부품이 따로 있는 게 아니라 모든 언어가 같은 가중치를 나눠 쓰기 때문이다. 3에서 커진 건 엔진(`vector_estimator`, 132MB → 257MB)을 키웠기 때문이었다. 목소리는 하나에 약 0.3MB라 골라 빼도 의미가 없었다.

파일별로 보면 크기는 두 곳에 몰려 있다.

| 파일 | 역할 | Supertonic 2 크기 |
| --- | --- | --- |
| `vector_estimator` | 음성의 특징을 만드는 엔진 | 132MB |
| `vocoder` | 특징을 실제 파형(소리)으로 바꿈 | 101MB |
| `text_encoder` | 글자를 읽을 수 있게 바꿈 | 27MB |
| `duration_predictor` | 소리 길이 예측 | 2MB |

## 시도와 버린 것

언어를 잘라 낼 수 없으니 남은 방법은 숫자 정밀도를 낮추는 **양자화**였다. ONNX Runtime의 동적 양자화(int8)와 fp16 변환으로 조합을 바꿔 가며 같은 문장을 만들고, 귀로 듣고 숫자로 확인했다.

| 시도 | 크기 | 결과 | 판단 |
| --- | --- | --- | --- |
| Supertonic 3 원본 | 380MB | 기준. 문장당 0.9~2.0초(CPU 4코어) | 너무 큼 |
| Supertonic 3 전부 int8 | 102MB | 음질이 깨지고 음량이 절반 | 버림 |
| Supertonic 3 엔진만 int8 | 172MB | 정상 | 여전히 큼 |
| Supertonic 2 원본 | 263MB | 문장당 약 0.5초 | 기준 |
| Supertonic 2 엔진 int8 | 144MB | 정상, 깔끔함 | 후보 |
| **Supertonic 2 엔진 int8 + vocoder fp16** | **93MB** | **원본과 SNR 40~46dB, 문장당 약 1초** | **채택** |
| Supertonic 2 전부 int8 | 67MB | 음량이 절반 | 버림 |

판단의 근거는 두 가지였다.

- **vocoder는 int8에 약하다.** 마지막에 파형을 직접 만드는 부분이라 작은 오차가 소리로 바로 나온다. vocoder까지 int8로 바꾼 버전은 모두 음량이 절반으로 떨어졌다. 그래서 vocoder만 fp16으로 바꿨다.
- **"깔끔하게 들린다"를 숫자로 확인했다.** 144MB가 93MB보다 깔끔하게 들렸는데, 두 버전은 vocoder 정밀도만 다르다. 같은 입력을 원본 vocoder와 fp16 vocoder에 넣어 출력 차이를 재 보니 SNR 40~46dB였다. 들린 차이는 크기 탓이 아니라 합성할 때마다 조금씩 달라지는 변동으로 봤다.

### 브라우저에서 다시 재 보니

위의 숫자는 모두 서버에서 파이썬(네이티브 ONNX Runtime, 4코어)으로 잰 값이었다. 실제 합성은 사용자 브라우저(onnxruntime-web, WASM)에서 돌아서, 서비스에 붙이기 전에 브라우저에서 다시 쟀다. 결과가 뒤집혔다.

| 판 | 받는 크기 | 문장 하나(스레드 1개) | 스레드 4개 |
| --- | --- | --- | --- |
| Supertonic 2 원본 | 263MB | 1.7~3.8초 | - |
| 엔진 int8 + vocoder fp16 (위에서 채택) | 93MB | **5.0~12.4초** | 3.0~4.0초 |
| 가중치를 fp16으로 담고 열 때 풀기 | 128MB | 1.6~3.4초 | 0.9~1.3초 |
| **가중치를 int8로 담고 열 때 풀기** | **65MB** | **1.4~3.5초** | **0.7~1.0초** |

질문 5개(2.8~7.7초 길이), 다섯 단계 합성, 이 서버의 Chromium에서 잰 값이다.

- **원인: 크기는 저장 방식이고 속도는 계산 방식이다.** 동적 양자화는 계산할 때마다 숫자를 int8로 바꿨다 되돌린다. 서버 CPU에는 이걸 빠르게 하는 전용 명령이 있어 오히려 빨랐다. 브라우저 WASM에는 그 명령이 없어 5배 느려졌다. 시간의 85%가 int8 엔진(`vector_estimator`)에서 나갔다.
- **해결 1: 담을 때만 작게.** 처음엔 가중치를 fp16으로 담고 모델 안에 Cast 노드를 넣어 열 때 fp32로 되돌렸다. ONNX Runtime이 세션을 만들 때 이 노드를 상수로 접어서, 계산은 원본과 같은 fp32로 한다. 128MB에 원본 속도(스레드 4개 0.9~1.3초)라 이 판으로 진행하기로 했다.
- **해결 2: 어차피 풀 거라면 더 작게 담는다.** 진행하기로 한 뒤 "열 때 어차피 푼다면, 담는 형식은 더 줄일 수 있지 않나"라는 질문이 나왔다. 열 때 푸는 방식에서 담는 형식은 계산 속도와 상관이 없다. 그러니 fp16(2바이트)이 아니라 int8(1바이트, 출력 채널마다 scale)로 담고 Cast·Mul로 풀어도 된다. 바로 시험해 보니 **128MB → 65MB**로 반이 됐고, 속도는 오히려 조금 빨랐다(0.7~1.0초). 93MB 판이 int8 때문에 느렸던 것과 달리, 이번 int8은 받는 파일에만 있고 계산에는 없다.
- **소리:** 합성할 때마다 시작 잡음이 달라 억양이 조금씩 바뀐다. 그래서 원본을 잡음만 바꿔 두 번 만든 차이(스펙트럼 12~15dB)를 기준으로 삼았다. 65MB 판은 원본과 3~7dB라 그 흔들림보다 작았고, 음량은 그대로였다(0.99~1.02배). 위 표의 "전부 int8 67MB"가 음량이 절반이었던 것은 계산까지 int8로 한 동적 양자화였기 때문이다.
- **스레드:** 브라우저는 교차 출처 격리(COOP/COEP 헤더) 없이는 코어가 많아도 스레드 1개만 준다. 헤더를 걸고, 밖에서 받는 파일(MediaPipe, ONNX Runtime 실행 파일, 모델)이 CORS·CORP로 계속 받아지는지 실제 흐름으로 확인했다.
- **화면 멈춤:** 합성은 웹 워커에서 돌려, 합성하는 동안 화면 끊김은 최대 67ms였다.

이 밖에 검토하고 버린 대안이다.

| 대안 | 버린 이유 |
| --- | --- |
| 클라우드 TTS | 글자당 과금 |
| VoxCPM2(OpenBMB, Apache 2.0) | 음질 최고, 목소리 복제 가능. 하지만 약 5GB라 GPU 서버가 필요 |
| 내 목소리로 만들기(Supertonic Voice Builder) | 유료 서비스였고, 회사 합병으로 닫힘 |
| Supertonic 3 유지 | 줄이면 음질이 깨지고, 2보다 나은 점이 크지 않음 |
| 93MB 판 유지(int8 계산) | 브라우저 WASM에서 5배 느림 |
| WebGPU | 그래픽 카드로 계산하면 더 빠를 수 있지만, 측정 환경에 진짜 GPU가 없어 재지 못함. 배포 뒤 실제 기기에서 잰다 |

## 결정과 이유

- **Supertonic 2를 가중치만 int8로 담은 65MB 판으로 브라우저(웹 워커)에서 합성한다.** 서버 TTS 비용이 0이 되고, 기기와 상관없이 같은 목소리가 나온다. 처음 고른 93MB 판은 브라우저 측정으로 바꿨다.
- **사이트에 교차 출처 격리 헤더를 건다.** 스레드 4개로 문장당 0.7~1.0초가 된다. 대가로 팝업 방식 로그인이 막혀, 로그인은 리디렉션 방식으로 붙인다.
- **목소리는 세션마다 6개(여자 셋·남자 셋) 중 하나를 뽑는다.** 면접관이 바뀌는 느낌을 주고, 같은 목소리에 질리지 않게 한다.
- **고정 질문도 미리 만든 음성 파일 없이 브라우저에서 합성한다.** 파일은 "모델을 받기 전에도 읽기" 위한 보험이었다. 그런데 모델은 면접 정하기 화면부터 받아 장치 확인 동안 준비되고, 그사이 질문 음성도 미리 만든다. 느린 PC와 느린 회선에서 시험했을 때도 첫 질문부터 바로 읽었다. 받지 못해도 브라우저 기본 음성으로 읽어 깨지는 경로가 없어, 목소리 6개 × 질문 수만큼의 파일을 관리할 이유가 없었다. 실제 기기 측정에서 첫 질문 전에 준비되지 않는 경우가 잦으면 다시 본다.
- **모델을 받지 못하거나 실패하면 브라우저 기본 음성으로 돌아간다.** 질문 읽기는 핵심 기능이라 깨지는 경로가 없어야 한다.
- **다운로드 시간은 흐름으로 숨긴다.** 2단계(질문 고르기)에서 질문이 정해지므로, 1·2단계 동안 모델을 받고 3단계(장치 확인) 동안 음성을 미리 만든다.
- **영어 용어는 따로 바꾸지 않고 그대로 읽힌다.** 한국어 모델이라 문장 속 영어("React", "useEffect") 발음이 다소 어색하다. 처음엔 질문을 만들 때 "리액트"처럼 한글로 적은 읽기용 문장도 같이 받으려 했다. 그런데 실제로 들어 보니 알아들을 수준이었고, 읽기용 문장을 만들면 질문마다 출력 토큰이 는다. 질문은 화면에도 글자로 떠서 소리가 조금 어눌해도 바로 알 수 있어 하지 않기로 했다.
- **라이선스(OpenRAIL-M)를 지킨다.** 무료·상업 사용이 가능하지만, AI 음성이라는 표시, 수정한 모델 파일에 라이선스 사본과 수정 표시, 이용약관에 사용 제한 조항이 필요하다. 원본 저장소가 보관(archived) 처리됐으므로 모델 파일은 직접 호스팅한다.

## 결과

| 항목 | 전 | 후 |
| --- | --- | --- |
| 모델 크기 | 380MB(Supertonic 3) | 65MB |
| 원본 대비 차이 | - | 원본을 두 번 만든 차이보다 작음(스펙트럼 3~7dB, 기준 12~15dB) |
| 문장 하나 생성(브라우저) | 5.0~12.4초(93MB 판) | 1.4~3.5초, 스레드 4개 0.7~1.0초 |

브라우저 숫자는 이 서버(4코어)의 Chromium에서 잰 값이다. 실제 폰은 더 느릴 수 있다.

## 한계와 다음 단계

- 실제 폰·PC에서 모델을 받는 시간과 문장 생성 시간을 재야 한다. 저사양 폰에서 느릴 수 있다.
- 65MB도 모바일 데이터로는 부담이다. 지금은 데이터 절약 모드일 때만 받지 않는다. 와이파이에서만 받거나 처음에 묻는 방식을 실제 기기 측정 뒤에 정한다.
- 모델 파일은 Cloudflare R2에 두고, CORS는 서비스 출처에만 연다. 파일 자체는 공개다(브라우저가 받아야 돌고, 원래 공개 모델). 측정 서버에서는 가장 큰 파일(25.8MB)을 2.5초에 받았지만, 한국에서 받는 실제 속도는 배포 뒤에 잰다.
- 지금은 R2 응답이 엣지에 캐시되지 않아 받을 때마다 R2 읽기로 센다. 배포 전에 캐시 규칙을 건다.
- 처음 쓴 측정(서버 CPU)이 실제 실행 환경(브라우저)과 달라 결정이 한 번 뒤집혔다. 성능 숫자는 실제로 돌아갈 환경에서 잰다.
- 클라우드 TTS를 썼을 때의 월 예상 비용을 계산해 절감액을 숫자로 남긴다.
