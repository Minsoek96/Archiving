# AI 피드백 프롬프트: 외워서 맞히던 평가를 처음 보는 문항으로 다시 쟀다

> 기존 평가 문항에서 오류 0이던 프롬프트가 처음 보는 문항에서는 **5% 넘게 틀렸다.** 프롬프트 예시가 평가 문항 문구와 겹쳐 있었기 때문이다(평가 오염). 처음 보는 문항 74개를 4번씩 돌려 다시 골라 판정 오류를 **16/296 → 8/296**(5.4% → 2.7%)으로 절반으로 줄였고, 흔한 페르소나 프롬프트보다 **2배 빠르면서** 지어낸 답안·근거 없는 점수가 없는 피드백을 만들었다.
>
> 상태: 코드 반영 완료, 머지 전(2026-10).

## 문제 상황

intervgym은 사용자가 면접 질문에 말로 답하면 AI가 피드백을 준다. 처음에는 흔히 쓰는 페르소나 프롬프트를 시험했다.

> "너는 15년차 면접관이야. 냉정하게 평가하고, 10점 만점 점수와 모범 답안을 보여 줘."

내용은 그럴듯했지만 연습용으로는 문제가 많았다.

- 길어서 끝까지 읽고 다음 답변에 반영하기 어렵다.
- 근거 없는 점수(1/10, 6.5/10)가 붙는다. 녹음 확인용으로 한 말에도 1점을 줬다.
- 모범 답안이 지원자가 하지 않은 경험·반성·수치를 지어 넣는다. 그대로 외우면 면접에서 거짓말이 된다.
- 받아쓰기 오인식("코호트"가 "고호트"로 받아써짐)을 지원자 실수로 지적한다.

그래서 목표부터 다시 정했다. **다음 답변을 실제로 낫게 하는 피드백**: 먼저 고칠 것 하나, 다시 답할 때 스스로 답해 볼 질문, 점수와 모범 답안은 없음. 그리고 기준 하나를 세웠다. **"일반 페르소나 프롬프트보다 나은 점이 하나라도 분명해야 한다."**

## 평가 방법

LLM 출력은 사람이 다 읽을 수 없어서 평가 방식부터 설계했다.

- **판정 오류:** 문항마다 정답지(좋은 답 / 고칠 답 / 정크)를 두고, 모델의 판정이 맞는지 센다. 문항마다 여러 번 돌려 흔들림까지 본다.
- **평가자 5명:** 회차마다 서로 다른 관점(신입 지원자, 경력 지원자, 면접관, 코치, 프롬프트 엔지니어)의 LLM 평가자 5명이 출력을 읽고 **문제를 인용과 함께 찾는다.** 승패나 점수는 매기지 않는다. LLM 심판의 승패 판정은 사람 판단과 어긋나는 경우가 많았기 때문이다.
- **최종 판단은 사람이 한다.**
- **응답 시간:** 답변 직후 기다리는 화면이라 속도도 품질만큼 본다.

## 원인 분석: 평가 오염

v1부터 v8까지 평가자 지적을 고쳐 가며 기존 문항 33개에서 판정 오류가 거의 0이 됐다. 그런데 평가자 한 명이 이렇게 지적했다.

> "프롬프트의 예시 문장이 평가 문항의 문구와 거의 같다. 이 문항들은 외워서 맞힐 수 있다."

확인하려고 프롬프트를 본 적 없는 문항을 다른 모델로 새로 만들어 돌렸다. 결과가 갈렸다.

| 문항 | v11 판정 오류 |
| --- | --- |
| 기존 문항(e·h, 프롬프트 예시와 겹침) | 0% |
| 처음 보는 문항 | 약 5% (16/296) |

같은 프롬프트가 아는 문항에서만 잘했다. 그 뒤로는 **처음 보는 문항으로만 고르기로 했다.** 문항 세트를 세 번 더 만들어(직무 56개, 74문항) 각 버전을 4번씩 돌렸다.

## 시도와 버린 것

처음 보는 문항에서 틀린 출력을 평가자와 함께 읽으며 공통 원인을 찾았다. 대부분 **지원자의 말을 비틀어 읽어서 생긴 억지 지적**이었다.

| 버전 | 바꾼 것 | 판정 오류(/296) | 판단 |
| --- | --- | --- | --- |
| v11 | 예시를 일반 문형으로 바꿈, 규범 위반 우선 | 16 | 오염 발견 |
| v12 | 가장 자연스러운 뜻으로 읽기("한 번씩"을 "매번"으로 읽지 않기), 질문이 정한 조건은 사실로 받아들이기 | 16 | 개선 없음 |
| v13 | 권한 밖 판단을 책임자에게 넘기는 건 올바른 대응으로 보기, "모르겠습니다"는 반드시 정크로 | 12 | 개선 |
| v14 | 문장 일부를 떼어 다르게 읽지 않기 | 15 | 차이 없음 |
| **v15** | 넘기는 행동 이름만 있는 얇은 답은 예외로 | **8** | **채택** |
| v16 | 좋은 답 판정 전에 감점 문장 점검 단계 추가 | 11 | 버림(약 4초 느려짐) |

이 밖에 시험하고 버린 것이다.

| 시도 | 버린 이유 |
| --- | --- |
| 쓴 뒤 스스로 점검하는 단계 | 응답이 약 2초 느려짐 |
| 다시 답할 질문을 틀 3개로 고정 | 질문이 뻔해지고 약 3초 느려짐 |
| reasoning effort medium·high | 12초·18초로 느려지는데 low보다 낫다고 갈리지 않음 |
| 지원 직무·경력을 맥락으로 추가 | 판정 오류가 5 → 10~12회로 늘고, 신입·경력에 따라 출력이 거의 달라지지 않음 |

정답지도 틀릴 수 있었다. 문항을 만든 모델은 "좋은 답"이라 했지만 평가자 5명이 모두 "신고가 늦어진다"고 짚은 문항이 있었다. 이런 2문항은 평가자 판단으로 정답지를 고치고, 판단이 갈린 1문항은 빼고 모든 버전을 같은 기준으로 셌다.

## 결정과 이유

- **v15를 채택했다.** 처음 보는 문항에서 오류가 가장 적고(8/296), 기존 문항도 0이며, 응답이 가장 빨랐다(중앙값 6~7초).
- **"답변인데 고칠 것이 비어 있음" 실패를 막았다.** v11에서는 "모르겠습니다" 같은 답에 296회 중 3회 이런 출력이 나와 오류(502)가 났다. v13부터 1,100회 중 0회다.
- **모델이 드물게 섞는 일본어를 서버에서 걸러 다시 받게 했다.** 5,482회 중 1회였다.
- **점수·모범 답안 금지 전제는 지켰다.** 페르소나가 나은 점("모르는 지원자에게 틀을 준다")도 있었지만, 그건 이 전제를 바꾸는 결정이라 보류했다.

## 결과: 페르소나 프롬프트와 블라인드 비교

처음 보는 38문항에서 두 출력의 이름을 가리고 순서를 섞어 평가자 5명에게 비교시켰다.

| 항목 | 우리 프롬프트(v15) | 페르소나 프롬프트 |
| --- | --- | --- |
| 지원자가 하지 않은 말 지적 | 거의 없음 | 있음(정확한 답을 틀렸다고 함) |
| 받아쓰기 오인식 지적 | 없음 | 있음 |
| 지어낸 모범 답안·근거 없는 점수 | 없음 | 있음 |
| 정직하게 밝힌 한계 | 유지할 점으로 지켜 줌 | 감점 |
| 응답 시간(중앙값) | 약 6~7초 | 약 14초 |
| 좋은 답 속 위험한 문장 하나 잡기 | 가끔 놓침 | 더 잘 잡음 |
| 오류가 여러 개인 답 | 하나에 집중 | 모두 나열 |

5명 모두 정확성과 읽기 부담에서는 우리 쪽, 빠짐없이 잡아내는 범위에서는 페르소나 쪽을 꼽았다.

## 한계와 다음 단계

- 좋은 답 속 위험한 문장 하나를 "고칠 것 없음"으로 넘길 때가 있다(6회 중 1~2회). 잡게 하는 단계를 넣으면 느려져서 아직 풀지 못했다.
- 같은 답을 여러 번 돌리면 핵심이 갈리는 문항이 남아 있다.
- 모르는 지원자에게 틀을 줄지는 설계 전제와 함께 정해야 한다.
- 수치는 gpt-6-luna(reasoning low) 기준이다. 모델을 바꾸면 다시 평가한다.

## 배운 점

- **평가 세트도 오염된다.** 프롬프트를 고칠 때 쓴 문항으로 프롬프트를 평가하면 점수는 계속 오르지만 실력은 그대로일 수 있다. 처음 보는 문항을 따로 두고, 그걸로만 고른다.
- **LLM 평가자에게는 판정이 아니라 문제 찾기를 맡긴다.** 승패는 흔들렸지만, 인용과 함께 찾은 문제는 대부분 사실이었다.
- **품질과 속도는 같이 잰다.** 품질을 올리는 단계마다 2~4초가 붙었고, 대부분 그만한 개선이 없었다.
